# EthixWeb India — Database Schema

## 1. Scope and principles

Use Neon PostgreSQL for persistent enquiry data. The schema must match the existing Contact form fields exactly: **Name, Email, Project Subject, Your Message**.

Do not add `phone`, `company`, `service`, `budget`, or `timeline` columns to the MVP unless the frontend is intentionally updated to collect those fields. Do not create fake leads in production.

Principles:
- UUID primary key.
- UTC-capable `TIMESTAMPTZ` timestamps.
- Explicit status constraint.
- Parameterized SQL for all runtime queries.
- Database credentials remain server-side.

## 2. `leads` table

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE IF NOT EXISTS leads (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(120) NOT NULL,
  email VARCHAR(254) NOT NULL,
  project_subject VARCHAR(180) NOT NULL,
  message TEXT NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'new'
    CHECK (status IN ('new', 'contacted', 'qualified', 'closed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_leads_created_at
  ON leads (created_at DESC);

CREATE INDEX IF NOT EXISTS idx_leads_status_created_at
  ON leads (status, created_at DESC);
```

`pgcrypto` provides `gen_random_uuid()` on supported PostgreSQL versions. If the target database already supports UUID generation without enabling an extension, use the supported built-in function.

## 3. Column definitions

| Column | Type | Rules / purpose |
|---|---|---|
| `id` | UUID | Primary key, generated by database |
| `name` | VARCHAR(120) | Required visitor name |
| `email` | VARCHAR(254) | Required email address |
| `project_subject` | VARCHAR(180) | Required project subject |
| `message` | TEXT | Required enquiry message |
| `status` | VARCHAR(20) | `new`, `contacted`, `qualified`, or `closed`; defaults to `new` |
| `created_at` | TIMESTAMPTZ | Creation time, generated by database |
| `updated_at` | TIMESTAMPTZ | Last modification time |

The API must update `updated_at` when a lead's status changes. This can be done explicitly in the update query; a database trigger is unnecessary for this small MVP unless other writers will update the table.

## 4. API-to-database mapping

| Existing form/API field | Database column |
|---|---|
| `name` | `name` |
| `email` | `email` |
| `projectSubject` | `project_subject` |
| `message` | `message` |

Keep any current frontend property naming stable and map it at the API boundary. Do not rename existing UI fields merely to match SQL naming.

## 5. Query examples

### Insert an enquiry

```sql
INSERT INTO leads (name, email, project_subject, message)
VALUES ($1, $2, $3, $4)
RETURNING id, name, email, project_subject, message, status, created_at;
```

### List recent enquiries

```sql
SELECT id, name, email, project_subject, status, created_at, updated_at
FROM leads
ORDER BY created_at DESC
LIMIT $1 OFFSET $2;
```

### Update status

```sql
UPDATE leads
SET status = $1, updated_at = NOW()
WHERE id = $2
RETURNING id, status, updated_at;
```

All values must be passed as query parameters. Never interpolate user input into SQL strings.

## 6. Data handling

- Do not store passwords, authentication tokens, or unnecessary visitor data in the `leads` table.
- Do not log full message bodies by default.
- Validate input length and format in the API before inserting.
- Use a bounded list query and add pagination as needed.
- Deletion should be performed only through an authenticated admin endpoint and after confirmation in the UI.
- No production seed data. An empty table is a valid initial state.
